## شرح مسئله

شما در حال پیاده‌سازی لایه **احراز هویت و مجوزدهی (Authentication & Authorization)** برای یک سیستم رزرواسیون بلیط سینما هستید.

سیستم از دو عملیات کلیدی پشتیبانی می‌کند:

1. **رزرو بلیط** – در دسترس تمام کاربران احراز هویت‌شده (`User` و `Admin`).
2. **اضافه‌کردن اکران** – فقط در دسترس کاربران با نقش `Admin`.

پس از ورود موفق، کاربر باید یک **JWT** دریافت کند که شامل موارد زیر باشد:

* اطلاعات هویتی (مانند `sub` یا `userId`)
* نقش کاربر (`role`)
* Scopeها
* اطلاعات زمانی و امنیتی (`iat`, `exp`, `iss`, `aud`)

سیستم باید هم **Role-based Authorization** و هم **Scope-based Authorization** را اعمال کند.

## قوانین و محدودیت‌ها

### قوانین عمومی

* تمام endpointهای محافظت‌شده باید JWT را به‌صورت کامل اعتبارسنجی کنند (امضا، انقضا، issuer و audience).
* وضعیت‌های HTTP باید به‌درستی برگردانده شوند:

  * `401 Unauthorized` برای توکن نامعتبر یا عدم وجود توکن
  * `403 Forbidden` برای توکن معتبر با دسترسی ناکافی

### قوانین دسترسی

#### رزرو بلیط

* نیازمند احراز هویت
* نقش‌های مجاز: `User` و `Admin`
* نیازمند scope مرتبط با رزرو بلیط

#### اضافه‌کردن اکران

* فقط نقش `Admin`
* نیازمند scope مرتبط با ایجاد اکران

### Best Practiceهای امنیتی (الزامی)

* هش کردن رمز عبور (مثلاً BCrypt)
* عدم ذخیره رمز عبور به‌صورت plaintext
* Access Token با عمر کوتاه (۱۵ تا ۶۰ دقیقه)
* استفاده از کلید امضای امن (عدم hardcode در سورس)
* اعتبارسنجی `iss` و `aud`
* عدم قرار دادن اطلاعات حساس در JWT
* عدم افشای اطلاعات امنیتی در پیام‌های خطا

موارد امتیازی (اختیاری):

* Refresh Token
* Rate Limiting روی Login
* لاگ امنیتی
* قفل شدن حساب پس از تلاش‌های ناموفق

## سناریوهای اصلی

### 1) ورود کاربر و دریافت JWT

* کاربر اطلاعات ورود را ارسال می‌کند
* در صورت صحت، JWT معتبر شامل role و scope صادر می‌شود

### 2) رزرو بلیط (کاربران احراز هویت‌شده)

* کاربر با JWT معتبر می‌تواند بلیط رزرو کند
* نبود توکن یا نبود scope مناسب → `401` یا `403`

### 3) اضافه‌کردن اکران (فقط Admin)

* فقط کاربران Admin مجاز هستند
* نبود نقش یا scope مناسب → `403`

### 4) سناریوهای منفی

* توکن نامعتبر یا منقضی
* نقش اشتباه
* scope ناقص

## قرارداد پیشنهادی API

> نام endpointها قابل تغییر است، اما رفتار باید یکسان باشد.

### احراز هویت

* `POST /api/auth/login`
* `POST /api/auth/register` (اختیاری)

### اکران‌ها

* `POST /api/screenings` (فقط Admin)
* `GET /api/screenings`

### بلیط‌ها

* `POST /api/tickets/reserve`

## نمونه ورودی/خروجی

### نمونه درخواست ورود

```http
POST /api/auth/login HTTP/1.1
Content-Type: application/json
```

### نمونه پاسخ ورود

```json
{
  "accessToken": "<JWT>",
  "tokenType": "Bearer",
  "expiresInSeconds": 3600
}
```
